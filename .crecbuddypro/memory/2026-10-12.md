## 产物通知 mac 不生效修复（10:50）

用户 mac 实测通知不弹。探针脚本证实：**WKWebView 里 Notification.permission 硬死在 denied，requestPermission 永远 denied**——WebKit 只在 Safari 给网页通知授权，嵌入式 webview 一律拒绝（WebView2/Windows 才支持）。我最初"双端都支持 Web API"的假设错了。

修复（双路由）：desktop_cmd 加 `show_notification` 原生桥（mac 用 osascript display notification，已实测可弹；Windows 兜底 PowerShell NotifyIcon）；前端 Web API 未授权时自动落原生桥（mac 无点击直达——osascript 无回调，点击直达仍是 WebView2 专属）；设置页识别原生路由后不再显示误导性的"权限被拒"警告。

⚠️ 平台知识沉淀：**跨平台 webview 能力差异要先探针验证再写代码**——WKWebView：网页通知✗、其他（如 clipboard 部分 API）也要留意；WebView2（Chromium 内）接近 Chrome 全量。

## 计划卡片跨会话残留修复（15:40）

用户报第二个问题：切走后卡片到处都在、回原会话异常。根因：卡片订阅 effect 空依赖数组——挂载时 fetch 一次后永不更新，切会话不重跑，旧 plan 状态跨会话残留。

修复：卡片接 chatId prop（仅作 effect 触发器），每次 URL 切换立即清空旧 plan + 重查 + 800ms 延迟补查（window.currentSessionId 滞后于 URL 切换）。

**⚠️ 双 ID 语义再次立功**：plan 后端按**库时间戳 session id** 存，不是 URL 的 chat UUID——查询必须用 window.currentSessionId，chatId 只能当触发器用，传给 getCurrentPlan 会查空。这坑第三次出现（GlobalSearch/PlanProgressCard/将来注意）。

用户报的"点击该任务的历史会话页面打不开"——需用户重测确认是否随本修复消失（卡片残留可能干扰了切换感知），若仍复现要具体现象（无反应/白屏/转圈）。

## 计划会话点不开修复（16:05）

用户复测：其他会话都正常打开，唯独想一想那条点击完全没反应。根因：**ChatSessionInitializer 只按 session.id 匹配 URL chatId**——经 resolveRealId swap 的会话 id 变成库时间戳、UUID 藏在 realId 扩展字段，UUID 查找落空 → 静默跳过切换（URL 其实变了但消息区不动，webview 无地址栏用户感知就是"没反应"）。未经历 swap 的会话 id 就是 UUID 所以能开——完美对上"唯独那一条"。

修复：查找按 id/realId/sessionId 三字段兜底。**双 ID 陷阱第四次现身**（GlobalSearch、PlanProgressCard、这次、第一次是 sessionApi 本身）——这个项目里"URL/侧栏用 UUID、库内部用时间戳"的分裂是系统性雷区。

## React #310 崩溃修复（16:40）——诊断边界一天回本

用户复现拿到错误详情：React #310（渲染间 hooks 数量不一致）。根因：下午加折叠功能时把 useState(collapsed) 插在了 early return **之后**——无计划渲染时跳过该 hook，SSE 推来计划后多跑一个 hook → React 中止渲染。切进想想一会话必崩（正是上午匹配修复让 SSE 计划流涌入该视图后触达的雷）。

修复：useState 移到组件顶部 + 警示注释。**教训：加 hook 时先看组件有没有 early return**。诊断边界（错误详情直接显示在崩溃页）保留——这次一天回本。
