# 小铁智友 × 对标 WorkBuddy 全流程闭环自动化方案

> 版本：v1.0（2026-09-28）
> 目标：建立"竞品跟踪 → 设计 → 开发 → 打包 → 部署 → 反馈"的可持续自动化闭环，
> 全面对标 WorkBuddy，功能差异及时补齐，竞品更新及时跟进。

---

## 一、总体架构：三层闭环

```
┌─────────────────────────────────────────────────────────┐
│  第一层：竞品情报闭环（每周）                              │
│  WorkBuddy 更新监控 → 差异分析 → 需求池 → 优先级评审        │
└──────────────────────┬──────────────────────────────────┘
                       ↓ 输入需求
┌─────────────────────────────────────────────────────────┐
│  第二层：研发交付闭环（每个迭代，1~2 周）                    │
│  设计 → 开发 → 自测 → CI 门禁 → 双平台打包 → 发布           │
└──────────────────────┬──────────────────────────────────┘
                       ↓ 交付版本
┌─────────────────────────────────────────────────────────┐
│  第三层：质量反馈闭环（每日）                               │
│  自动更新 → 用户反馈收集 → Bug 池 → 回归第一层              │
└─────────────────────────────────────────────────────────┘
```

## 二、第一层：竞品情报闭环（对标 WorkBuddy）

### 2.1 竞品动态监控（自动化，每周一执行）

用定时任务自动抓取 WorkBuddy 的公开信息源，产出周报：

| 信息源 | 内容 | 监控方式 |
|--------|------|----------|
| 官方更新日志（workbuddy.cn/docs） | 功能更新、版本号 | 每周抓取 diff |
| 腾讯云开发者社区"WorkBuddy"标签 | 深度功能解析文章 | 每周搜索新文章 |
| 应用商店（Win/Mac）版本说明 | 用户可见的更新 | 每周检查版本号 |
| 产品百科/新闻稿 | 大版本、企业版动向 | 每月检索 |

**实现**：创建定时任务（cron），每周一 9:00 自动执行 WebSearch + WebFetch，
产出《WorkBuddy 周报》存入 `docs/competitive/weekly/YYYY-MM-DD.md`，
新功能自动与我们的功能清单比对，标出「我们有/我们没有/他们新加」。

### 2.2 功能差异基线表（v1.0，2026-09-28 基于最新情报）

以下是 WorkBuddy 当前功能版图与小铁智友现状的首次对比：

| 能力域 | WorkBuddy | 小铁智友现状 | 差距 | 补齐优先级 |
|--------|-----------|-------------|------|-----------|
| **自主规划执行** | 自然语言→任务拆解→工具调用→自我校验 | ✅ 已有（ReAct agent + 工具链） | 基本持平 | — |
| **本地文件操作** | 授权目录读写、批量处理 | ✅ 已有（工作区 + 文件工具） | 基本持平 | — |
| **三种工作模式** | Ask（问）/ Plan（想）/ Craft（做）| ⚠️ 部分有（有 plan 模式雏形） | 缺 Ask/Craft 明确分层 | P1 |
| **多模态** | 图文表格代码理解与生成、拍照→文档 | ⚠️ 有图片理解，缺视频生成等 | 中 | P2 |
| **专家系统** | 140+ 专家 + 专家团并行 | ⚠️ 12 位中铁专家（垂直深度强）| 数量差距大，但行业垂直是我们的差异化 | P2（走"深"不走"广"） |
| **技能系统** | SkillHub 市场 + Skill-creator 一键封装 | ⚠️ 有技能框架，无市场无自封装 | 大 | P2 |
| **连接器/MCP** | 腾讯文档/企微/飞书/钉钉/GitHub 等 | ⚠️ 框架支持 MCP，连接器数量少 | 中 | P1（优先接中铁内部系统） |
| **跨端远程调度** | 5 大 IM 远程指挥 PC、三端同步 | ❌ 钉钉/企微通道有，移动端体验弱 | 大 | P2 |
| **定时任务** | 定时抓取/巡检/日报 | ✅ 已有（cron 系统） | 持平 | — |
| **企业版** | 团队记忆、AI 资产管理、企微深度集成 | ❌ 无 | 大（但短期非重点） | P3 |
| **平台覆盖** | Win/macOS/鸿蒙/麒麟/UOS + App/小程序 | Win/macOS | 缺国产系统适配 | P3 |
| **检查更新** | 自动更新 | ❌ **当前失效**（详见 3.3） | 大 | **P0** |

**结论**：短期打"行业深度"（中铁 12 专家 + 工程场景），中期补模式分层和连接器，
更新链路（P0）必须先修好——否则所有功能迭代都到不了用户手上。

### 2.3 差异跟进机制

1. 周报发现 WorkBuddy 新功能 → 24h 内完成评估（抄/不抄/怎么抄）
2. 评估结果录入 `docs/competitive/gap-log.md`，注明决策理由
3. 决定跟进的 → 进需求池，与日常需求一起排优先级（见 2.4）

### 2.4 需求优先级模型

```
P0 阻断性：功能坏了用户用不了（如检查更新失效）
P1 竞争性：对标差距大且用户高频使用（工作模式、连接器）
P2 增强性：有差距但可后补（专家数量、技能市场）
P3 战略性：长线布局（企业版、国产系统）
每两周评审一次需求池，P0 随时插入
```

## 三、第二层：研发交付闭环

### 3.1 设计环节

每个需求进入开发前，产出轻量设计卡（不超过一页）：

```markdown
## 需求：XXX
- 对标：WorkBuddy 的 XX 功能（附链接/截图）
- 用户场景：谁在什么情况下用它干什么
- 交互设计：UI 改动点（附手绘/原型）
- 技术方案：动哪些模块、数据流
- 验收标准：怎么算做完（可测试的条目）
```

设计卡存 `docs/design/YYYY-MM-DD-<需求名>.md`，用户确认后进开发。

### 3.2 开发环节（已在执行的规范）

- 分支：`crec-desktop`（主开发分支）
- 提交规范：`feat/fix/refactor(scope): 描述`
- 自测：macOS 本地 `dist/小铁智友.app` 验证后再打包

### 3.3 三个已知 Bug 的修复方案（P0，本周内）

#### Bug 1：调用上限导致会话自动终止

**根源**：`src/qwenpaw/config/config.py:763` 的 `max_iters` 默认 **100**——
ReAct agent 推理-行动循环满 100 次后强制终止本轮回复（代码里已有提示语
"本轮调用已达最大次数"，但用户感知是"会话崩了"）。

**修复方案**（三管齐下）：
1. **上限提高**：默认值 100 → 500（对齐 WorkBuddy 的长任务体验）
2. **可配置**：设置页暴露"最大连续执行次数"滑块（50~1000）
3. **优雅续跑**：达到上限时不终止会话，而是暂停并提示
   "已达 N 次调用，输入'继续'接着跑"（保留上下文，一键续）——
   这是体验上的关键差异，WorkBuddy 到上限是硬截断，我们可以做得更好

#### Bug 2：页面偶发卡死（切页恢复）

**根源**（基于前期排查经验，PDF 卡死已修，剩余嫌疑）：
- 长对话的虚拟列表渲染阻塞主线程
- 流式输出时高频 setState 导致 React 渲染堆积
- WebView2/WKWebView 的内存压力（长会话图片多）

**修复方案**：
1. 复现路径记录：让用户反馈时截图 + 说明操作序列（加"复制诊断信息"按钮）
2. 前端加全局卡死检测：`requestIdleCallback` 超时 5s 无响应 → 自动降级
   （暂停流式渲染、显示"正在恢复"提示条），无需用户切页
3. 长会话虚拟列表 + 图片懒加载改造（治本）

#### Bug 3：检查更新失效（P0 中的 P0）

**根源**（已查明）：
- 更新服务器是 `io.crec.cn:30090`（MinIO 网关），manifest.json 还停在 **1.1.6**（8月12日），
  而我们已发 1.1.7 —— 发布链路断了：新版本从未更新过 manifest
- `publish.sh` 依赖 `mc` 客户端，但该网关的 S3 API 端口未对外开放，mc 无法使用
- 网页控制台上传大文件会在"合并分片"最后一步报 network error

**修复方案**：
1. **短期（本周）**：手动发布流程固化——发布时人工更新 manifest.json（版本号/SHA256/
   下载地址/更新说明），用 Console 网页或管理员提供的通道上传 zip，验证客户端能收到更新提示
2. **中期（2周内）**：打通自动上传——找运维开通 S3 API 外网端口（拿到端口后 10 分钟
   配好 mc alias + publish.sh 全自动）；或退而求其次用 Console API + 登录会话上传
3. **验收标准**：客户端打开"检查更新"→ 提示 1.1.8 → 下载 → SHA256 校验 → 安装成功

### 3.4 打包环节（已全自动化 ✅）

流程已验证通过，固化为标准动作（详见 `scripts/pack/` + GitHub Actions）：

```
代码合并 → push fork → API 触发 Actions →
  [Windows] conda-pack + NSIS + 损坏检测 + 导入冒烟测试（20min）
  [macOS]   PyInstaller 本地包（即时验证）
→ 下载 artifact → 双平台安装包
```

两道质量门禁（compileall 损坏检测、后端导入冒烟测试）已防住历史上
"包能构建但装上就崩"的三类问题，勿删。

### 3.5 发布环节（本周补齐）

```
1. 更新版本号 src/qwenpaw/__version__.py（1.1.7 → 1.1.8）
2. 双平台安装包产出（3.4）
3. 上传 MinIO ai-client-package 桶（短期人工，中期自动）
4. 更新 manifest.json：version / sha256 / size / releaseNotes（中英文）
5. 验收：旧版本客户端 → 检查更新 → 全流程走通
6. 发布记录登记 docs/releases/v1.1.8.md（改了什么、对应竞品哪个功能）
```

**发布纪律**：每个迭代必须递增版本号；manifest 与安装包同步更新，不再出现
"包发了 manifest 没动"的断链。

## 四、第三层：质量反馈闭环

### 4.1 用户反馈收集（自动 + 手动）

| 渠道 | 方式 | 频率 |
|------|------|------|
| 桌面端"反馈"入口 | 应用内按钮，一键带上日志和版本号 | 实时 |
| 日志回收 | 用户同意后上传 `~/.qwenpaw/qwenpaw.log` 尾部 | 随反馈 |
| 群内反馈 | 用户手动截图 | 每日收集 |
| 崩溃自报告 | 启动失败页（已实现）显示 traceback，用户截图 | 实时 |

### 4.2 Bug 分诊流程

```
反馈进来 → 复现/定位（用日志+版本号）→ 按严重度分级
  S1 崩溃/卡死/数据丢失 → 当周修，走紧急发布
  S2 功能失效（如更新链路）→ 下个迭代修
  S3 体验问题 → 需求池排队
所有修复必须有复现路径和验证记录
```

### 4.3 回归防线

- 每次发版前：跑一遍**核心场景 checklist**（登录/对话/专家/工作区/文件下载/更新检查）
- 已修 bug 录入回归清单，每次发版复查，防止复发（尤其打包链路的三只虫）

## 六、关键指标（衡量闭环是否转起来）

1. **更新触达率**：发版后 7 天内，活跃用户升级比例（目标 >80%）——依赖 Bug3 修复
2. **需求交付周期**：从需求确认到用户用上（目标 ≤2 周/迭代）
3. **竞品跟进速度**：WorkBuddy 新功能发布到我们完成评估（目标 ≤1 周）
4. **崩溃/卡死率**：每周反馈的 S1 数量（目标持续下降）
5. **打包一次成功率**：Actions 全绿率（目标 >95%，当前 ~60%，因网络和依赖漂移）
